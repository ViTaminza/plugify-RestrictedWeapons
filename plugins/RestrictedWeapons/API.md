# RestrictedWeapons — Plugify API design

The `RestrictedWeapons` core of the Pisex `cs2-restricted_weapons` Metamod:Source plugin, ported to
a Plugify C++ plugin. This document is the contract between the plugin
(`plugins/RestrictedWeapons`) and the module that used to talk to it through the `IRWApi` interface
of `ref/src/cs2-restricted_weapons/Core/include/restricted_weapons.h` — i.e. the
`restricted_weapons_vip` module (ported later, `ref/src/cs2-restricted_weapons/VIP_Module`).

## 1. Files

| Path | Role |
| --- | --- |
| `RestrictedWeapons.pplugin.in` | Plugify manifest: 2 exported methods (group `callbacks`). Dependencies: `s2sdk >= 2.18.2`, `polyhook >= 2.5.2`, optional `hudmenu`. |
| `include/external/plugify/include/RestrictedWeapons/**` | Consumer headers **generated by `bin/plugify-gen`** from the manifest (never edited by hand). |
| `include/external/plugify/include/RestrictedWeapons/RestrictedWeapons.cpp` | The `__RestrictedWeapons_*` binding slots. **Must be compiled into every consumer plugin** (the `rw_bindings` OBJECT target does that); the Plugify module fills them when the plugin is loaded. |
| `include/rw_api.hpp` | Hand-written consumer wrapper that restores the `IRWApi` shape (`std::function` callback, `const char*`, the original method name). |
| `src/rw_core.hpp` / `.cpp` | Engine-free core (config model, threshold/decision rules, defindex table) — static library `rw_core`. |
| `src/plugin.cpp` | The plugin: config/phrases loading, the `CanAcquire` polyhook detour, player/weapon counting, chat/sound, the two exports. |
| `assets/gamedata.jsonc` | The `CCSPlayer_ItemServices::CanAcquire` signature (own gamedata, see §4). |
| `sym/version_script.lds` | Export list of the shared library (keep in sync with the manifest). |
| `tests/rw_core_tests.cpp` | Tests of the core against the live config. |
| `tests/rw_api_tests.cpp` | Tests of the consumer wrapper with stubbed binding slots. |

## 2. Boundary rules

1. **Types.** Only `plg::string` and plain C function pointers cross the boundary.
2. **`PluginId` registration becomes a Register/Unregister pair.** The original
   `IRWApi::HookOnWeaponRestricted(callback)` kept the callbacks of all modules in one
   `std::vector` and asked *every* listener on each blocked weapon (`SendOnWeaponRestrictedCallback`
   ORs the results: any `true` unblocks). The Plugify pair keeps that: every registered callback
   pointer is called; registering the same pointer again is a single entry, `*_Unregister` removes
   it (idempotent). The consumer wrapper hides this completely.
3. **`std::function` becomes a plain C callback** `bool (*)(int32, const plg::string&)`. The
   wrapper's trampoline converts `plg::string` to `const char*` and swallows exceptions.
4. **No exceptions** escape into the engine: every trampoline of the wrapper and every exported
   function catches (`catch (...)` + log through `plg::Log`).

## 3. The one `IRWApi` method as Plugify exports

| Pisex | Export (Plugify) | Group |
| --- | --- | --- |
| `void HookOnWeaponRestricted(OnWeaponRestrictedCallback)` where the callback is `std::function<bool(int iSlot, const char* szWeapon)>` | `OnWeaponRestricted_Register(WeaponRestrictedCallback)` / `OnWeaponRestricted_Unregister(WeaponRestrictedCallback)` where `WeaponRestrictedCallback = bool(*)(int32 slot, const plg::string& weapon)` | callbacks |

`OnWeaponRestricted` fires when a restriction *would* block the weapon a player is about to pick up
or buy (the same point the original's `CanAcquireListener` used):
`slot` is the acquiring player, `weapon` the classname (`weapon_awp`). Returning `true` means
"this plugin unblocked the weapon"; the core lets the weapon through when at least one listener
returned true **and** `unblock_type` allows it (`0`: always, `1`: only when the weapon's limit is
> 0) — exactly the original's rule.

## 4. Using the API from the VIP module

Include paths (module `CMakeLists.txt`):

```cmake
target_include_directories(restricted_weapons_vip SYSTEM PRIVATE
        "${CMAKE_SOURCE_DIR}/plugins/RestrictedWeapons/include"                          # rw_api.hpp
        "${CMAKE_SOURCE_DIR}/plugins/RestrictedWeapons/include/external/plugify/include" # generated
        "${CMAKE_SOURCE_DIR}/sdk/include")
target_link_libraries(restricted_weapons_vip PRIVATE
        $<TARGET_OBJECTS:rw_bindings> ...)   # or list rw_bindings in target sources
```

Porting recipe (VIP_Module/restricted_weapons_vip.cpp):

```cpp
// before (Metamod)
IRWApi* g_pRWApi = (IRWApi*)g_SMAPI->MetaFactory(RW_INTERFACE, &ret, NULL);
g_pRWApi->HookOnWeaponRestricted(OnWeaponRestricted);

// after (Plugify)
#include <rw_api.hpp>
restricted_weapons::RWApi* g_pRWApi = &restricted_weapons::RWApi::Get();
g_pRWApi->HookOnWeaponRestricted(OnWeaponRestricted);
```

Everything else keeps its original spelling; the callback signature
`bool OnWeaponRestricted(int iSlot, const char* szWeapon)` stays unchanged. The `szWeapon`
pointer is valid for the duration of the call (it points into a local string in the trampoline),
which is how the original passed the classname of its `GetWeaponByDefIndex` table (a string
literal) — the module only `strstr`s it.

## 5. The engine side

`src/plugin.cpp`:

* **Config** (`restricted_weapons.ini`, resolved through `pisex::ResolvePath` to
  `<configs>/RestrictedWeapons/restricted_weapons.ini`): loaded at plugin start and on every map
  start (the original's `StartupServer()` ran on every level init, so `LoadConfigs()` saw the
  current map name — that is what makes the map-specific block work). Missing file: the previous
  values stay, one warning.
* **Phrases** (`restricted_weapons.phrases.txt` → `<configs>/RestrictedWeapons/translations/`): the
  `block` / `block_team` messages and the weapon display names; the server language is used (the
  production file has no `language` key).
* **The `CanAcquire` detour**: `polyhook::HookDetour` on the address of
  `CCSPlayer_ItemServices::CanAcquire` resolved from the plugin's own `gamedata.jsonc`
  (s2sdk `LoadGameConfigFile`/`GetGameConfigSignature`). Arguments declared
  `{Pointer, Pointer, Int32, Pointer}` = `(this, CEconItemView*, AcquireMethod, uint* pLimit)`;
  the `Pre` callback replaces the engine's result with `NotAllowedByMode` and returns
  `ResultType::Supercede` (the original function is **not** called — the same thing the Pisex
  utils hook did through `SendCanAcquirePre` + `bHandled`).
* **Counting** (`GetNiggers`/`GetWeaponCount` of the original): players via `GetPlayerController`
  (the original's `FromSlot()` non-null check) + `IsFakeClient` + `GetTeam`, weapons via
  `s2sdk::GetClientWeapons` (the `m_hMyWeapons` walk) + `pisex::GetEntityClassname`. The item
  defindex is read from `CEconItemView::m_iItemDefinitionIndex` through the schema system.
* **Announcement**: at most one chat message per player per `interval_message` seconds
  (`g_iLastMessage` of the original), plus the `block_sound` sound event played to that player only
  (`s2sdk::EmitSoundToClient`, the single-recipient `IPlayersApi::EmitSound`).

### Deviations (all deliberate)

* The utils plugin used to own the `CanAcquire` hook for every Pisex plugin; in the Plugify world
  `pisexcompat` does not cover `AddCanAcquire*` (see its README §6), so this plugin installs the
  hook itself. A second plugin hooking the same function would find the existing detour via
  `polyhook::FindDetour`; only RestrictedWeapons needs it today.
* `GetNiggers` counted `CCSPlayerController::FromSlot(i)` slots; empty slots are skipped through
  `GetPlayerController(i) == 0` (an empty slot has no controller entity).
* The sound is emitted through the s2sdk binding that takes an entity *handle*; the original passed
  a `CEntityIndex`. `pisex::EntIndexToEntHandle` converts (same entity, same sound, same
  single-recipient filter).
* Config reload also happens once at plugin start (for a plugin loaded into a running map); the
  original only loaded on level init.

## 6. The engine-free core (`rw_core`)

`rw_core` is a static library (pisexcompat's KV1 parser, no s2sdk/Plugify types) so the rules are
unit-testable:

* **`Config`** — the `restricted_weapons.ini` model: `blockSound`, `typePlayers`, `specPlayers`,
  `typeWeapons`, `unblockType`, `intervalMessage` and `restrictions` (threshold → weapon → limit).
* **`ParseConfig(root, mapName)`** — the original `LoadConfigs()`: the `"all"` block first, then the
  map block (overwriting entries). The threshold keys are `atoi()`-ed like the original, so a
  non-numeric key becomes threshold 0.
* **`BestFitThreshold`** — the original's loop: the largest threshold ≤ player count, -1 when none.
* **`Evaluate`** — `CanAcquireListener`'s rule: no threshold / no entry for the weapon →
  Allowed; `count < limit || limit == -1` → Allowed; otherwise Restricted with that limit. The
  VIP unblock, the message interval, the sound and the engine result are the plugin's job.
* **`WeaponByDefIndex`** — the original's defindex table, default `weapon_knife`.

## 7. Tests

`tests/rw_core_tests.cpp` — parses the **live** production config (thresholds 0/4/7/10/12,
`weapon_awp` limits 0/1/2/3/-1), checks every setting, the best-fit threshold over 0..64 players,
the decision rules (allowed below the limit, blocked at it, `-1` unlimited, unlisted weapons,
threshold 0), a synthetic map-override file and the empty-file defaults; plus the defindex table.
`tests/rw_api_tests.cpp` — the consumer wrapper with stubbed binding slots: null-slot safety,
plg ↔ `const char*` conversion, register/replace/unregister and the trampoline's exception safety.
